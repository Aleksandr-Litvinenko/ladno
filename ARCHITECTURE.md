# Архитектура «Ладно» 0.1.0

## Назначение и границы

Версия 0.1.0 — статическое однопользовательское демо. Она связывает счета, складские движения и управленческие отчёты, но не пытается заменить бухгалтерский контур или реальную ERP.

Основные технические ограничения намеренные:

- нет backend и серверной базы данных;
- нет аутентификации и ролей;
- состояние хранится в `localStorage`;
- нет сетевого обмена с 1С;
- все примеры используют синтетические данные.

## Предметная модель

### Счёт поставщика

Содержит контрагента, номер и дату, срок оплаты, назначение, сумму, налоговую часть, статус согласования и сведения об оплате. Переходы статуса образуют рабочую цепочку: регистрация → согласование → платёжный календарь → оплата.

### Счёт покупателю

Содержит покупателя, срок оплаты, сумму, состояние отгрузки и поступившую оплату. На его основе видны ожидаемое поступление, просрочка и остаток задолженности.

### Складское движение

Изменяет количественный остаток и описывает тип операции: поступление, отгрузка или перемещение между складами. Движение сохраняет ссылку на документ-основание, если оно есть. Резервирование и ручные корректировки в версии 0.1.0 не реализованы.

### Денежное событие

Содержит дату, направление, сумму, категорию, плановый или фактический признак и ссылку на документ. Эта модель питает Cash Flow и платёжный календарь.

## Правила отчётов

### P&L

P&L строится по принципу начисления на демонстрационных операциях:

```text
управленческий результат = выручка − себестоимость − операционные расходы
```

Отчёт не проверяет требования РСБУ, МСФО, налогового или бухгалтерского учёта.

### Cash Flow

Cash Flow группирует фактические денежные события по направлению и категории. Плановые события показываются отдельно, чтобы не смешивать ожидание с совершённым движением денег.

### Платёжный календарь

Календарь использует неоплаченные остатки и сроки счетов. Для каждого периода рассчитываются ожидаемые поступления, выплаты и прогнозный чистый поток. Это иллюстрация управленческого сценария, а не банковский прогноз.

## Хранение и версия данных

Демо хранит JSON в `localStorage` под собственным versioned-ключом. Схема должна содержать номер версии, чтобы несовместимые изменения можно было распознать и предложить пользователю безопасный сброс демоданных.

`localStorage` не даёт транзакционности, серверной синхронизации, шифрования, аудита и резервного копирования. Поэтому туда нельзя помещать реальные финансовые или персональные данные.

## Контракт совместимости с 1С OData

Нормализованный объект может хранить происхождение без привязки интерфейса к русскому имени метаданных:

```json
{
  "source": {
    "system": "1c-odata",
    "entitySet": "replace-with-metadata-entity-set",
    "refKey": "00000000-0000-0000-0000-000000000000",
    "dataVersion": "optional-source-version"
  }
}
```

Правила будущего адаптера:

1. Сначала прочитать `$metadata`, не угадывать имена entity sets.
2. Использовать allowlist разрешённых справочников, документов и регистров.
3. Запрашивать только необходимые поля через `$select` и ограниченные фильтры.
4. Обрабатывать `@odata.nextLink`, таймауты, недоступность и частичные ответы.
5. Нормализовать даты в ISO 8601, суммы — в числовое значение плюс валюту.
6. Сохранять `Ref_Key` как внешний идентификатор, не подменяя им внутренний ID.
7. В первой интеграционной версии разрешить только чтение; методы записи блокировать структурно.

Версия 0.1.0 реализует только форму данных и демонстрационный слой. Она не выполняет HTTP-запросов к 1С.

## Целевая серверная граница

Когда появится live OData, браузер не должен получать URL с credentials и обращаться в 1С напрямую. Планируемая схема:

```text
браузер
   │ HTTPS, собственная сессия
   ▼
API «Ладно»
   │ allowlist, timeout, аудит, read-only HTTP
   ▼
стандартный OData 1С
```

Учётные данные хранятся только в серверном secret store или `.env`, не попадающем в Git. API проверяет права пользователя, ограничивает объём ответа и не принимает произвольный OData URL от клиента — иначе возможны SSRF и утечка данных.
